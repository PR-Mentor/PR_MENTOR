# PR Mentor backend

FastAPI service for the frontend review workspace. API schemas and routes are the stable boundary; ingestion, analysis, AI, and storage implementations can be replaced behind their current interfaces.

## Run locally

From this directory, create and activate a virtual environment, install dependencies, and start the service:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Copy `.env.example` to `.env` and export the desired values in the shell (the service intentionally does not load dotenv files implicitly). `PR_MENTOR_STORAGE` selects `sqlite` (default) or `mongodb`; the service does not silently fall back if the selected database is unavailable. SQLite uses `PR_MENTOR_DATABASE_PATH`, defaulting to `backend/data/pr_mentor.sqlite3`. MongoDB requires `MONGODB_URI`; `MONGODB_DATABASE` defaults to `pr_mentor`. `GITHUB_TOKEN` is optional. AI needs both `LLM_API_KEY` and `LLM_MODEL`; the OpenAI-compatible endpoint may be changed with `LLM_API_BASE_URL`. `PR_MENTOR_CORS_ORIGINS` is a comma-separated allowlist. `PR_MENTOR_HTTP_TIMEOUT` is bounded to 1–60 seconds.

Run tests from this directory with `python -m pytest -q`. Tests use temporary SQLite files, `mongomock`, and mocked external services; they need no GitHub token, LLM key, MongoDB server, or production database.

### MongoDB configuration and migration

Set `PR_MENTOR_STORAGE=mongodb`, `MONGODB_URI`, and optionally `MONGODB_DATABASE` to enable MongoDB. For Atlas, use the Atlas-provided `mongodb+srv://` URI and keep TLS certificate validation enabled. Local development can use `mongodb://localhost:27017`. The backend uses PyMongo and `dnspython` for SRV URIs, with bounded connection, server-selection, and socket timeouts. The process-level client is closed during FastAPI shutdown. `/api/health/ready` checks the currently selected storage; liveness remains independent of database availability.

Never commit a real connection URI, print it to logs, or disable TLS certificate validation. Store production credentials in the deployment secret manager and use a least-privilege database user. MongoDB connections and writes are only made by the backend; the browser uses the existing HTTP API.

The migration command is explicit and repeatable. It reads, but never changes or deletes, the SQLite source:

```powershell
$env:PR_MENTOR_STORAGE = "mongodb"
$env:MONGODB_URI = "<your-secret-uri>"
python -m scripts.migrate_sqlite_to_mongodb --source .\data\pr_mentor.sqlite3
```

The default source path is `PR_MENTOR_DATABASE_PATH`. Migration is never run at application startup. Reviews are upserted by `review_id`; saved URLs and learning attempts use stable unique keys so rerunning the command does not duplicate them.

Collections include `reviews`, `saved_pull_requests`, `learning_attempts`, `auth_users`, `auth_sessions`, `auth_rate_limits`, and `review_jobs`. Idempotent indexes enforce unique account/session/job identifiers and owner-scoped saved URLs, and support newest-first history queries. Review, saved-link, and learning records are scoped to the authenticated account. Legacy records with no determinable owner remain preserved but are not exposed to newly registered accounts.

## API contracts

- `GET /api/health` is a liveness check; `GET /api/health/ready` verifies SQLite can open.
- `POST /api/reviews/analyze` accepts `{ "url": "https://github.com/owner/repo/pull/42", "mode": "demo" | "live", "include_learning": true, "include_suggested_fixes": false }`. `pull_request_url` is also accepted for compatibility. Responses use `schemas/review.py`, `schemas/finding.py`, and `schemas/issue.py`, including explicit `is_demo`, analysis provenance, tool statuses, warnings, verification counts, and diff files. `findings` remains the ungrouped, backward-compatible list of source findings. `canonical_issues` groups reconciled `FindingObservation` records; each observation retains its original finding and source/tool/provider provenance. `unique_issue_count` counts canonical groups and `raw_observation_count` counts linked source observations. Legacy records return an empty `canonical_issues` list and a null `unique_issue_count`; their `findings` are preserved and their raw count is represented by the findings list length. Read compatibility adds response defaults without rewriting stored records.
- `GET /api/reviews/history?limit=50`, `GET /api/reviews/{review_id}`, and `GET /api/reviews/{review_id}/diff` read persisted review records. History includes demos by default; `include_demo=false` returns the account's non-demo records for profile views.
- `GET /api/reviews/saved`, `POST /api/reviews/saved` with `{ "url": "..." }`, and `DELETE /api/reviews/saved/{saved_id}` manage saved PR links.
- `GET /api/learning/exercises`, `GET /api/learning/exercises/{exercise_id}`, `POST /api/learning/exercises/{exercise_id}/submit` with `{ "answer": "..." }`, `GET /api/learning/progress`, and `GET /api/learning/history` serve authored exercises and persistent progress. Answers are omitted until submission.
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, and `GET /api/auth/me` provide local account sessions. Email ownership is not verified; password recovery and GitHub OAuth are not available.
- `POST /api/reviews/jobs` queues a durable background review; `GET` and `DELETE /api/reviews/jobs/{job_id}` read or cancel the current account's queued job. The worker runs separately with `python -m app.review_worker` and must be supervised in deployment.
- `POST /api/reviews/{review_id}/issues/{issue_id}/fixes/{fix_id}/validate` performs bounded static validation for an eligible suggested fix and appends a report to its history. Generated-test execution is not triggered by this endpoint.
- `POST /api/reviews/{review_id}/issues/{issue_id}/fixes/{fix_id}/generate-tests` returns snapshot-bound, statically screened candidates. `POST /api/reviews/{review_id}/issues/{issue_id}/fixes/{fix_id}/tests/execute` accepts one candidate and an `Idempotency-Key`, rechecks the current fix snapshot, and queues isolated execution. `GET` and `DELETE /api/reviews/execution-jobs/{execution_id}` return owner-scoped status/results or request cancellation.
- `POST /api/reviews/{review_id}/issues/{issue_id}/fixes/{fix_id}/semantic-review` requests a structured AI assessment for the current eligible fix. It is an assessment, not a verification result.
- `GET /api/learning/insights` and `GET /api/analytics/me` return personal aggregates with demo reviews excluded. Analytics includes exact account-owned live review-record, distinct live pull-request, and live finding counts; category, fix, and validation measures use at most the latest 100 non-demo review records. `GET /api/workspaces/{workspace_id}/learning-insights` returns separate aggregates over at most 100 explicitly shared reviews and requires workspace membership. Insights connect finding categories with fix decisions and validation outcomes; they are descriptive evidence, not skill scores. `/api/repositories/{owner}/{repository}/intelligence?ref=<full-commit-sha>` returns bounded repository structure analysis for a public repository.

FastAPI validation and HTTP errors use the standard `{ "detail": ... }` shape consumed by the frontend. Fixed paths are declared before dynamic review IDs.

### Canonical issue explanation contract

`CanonicalIssue.explanation` is optional and may be `null`. When present, its structured fields are `summary`, `why_it_matters`, `root_cause`, `correction`, optional `code_example` (`before`, `after`, and optional `language`), `concept`, `learning_resources`, and `caveats`. Explanation prose is bounded to 2,000 characters per field; each code side is bounded to 4,000 characters. A resource title is limited to 120 characters, its description to 300, and its URL to 500. Up to five resources and five caveats are allowed; each caveat is limited to 500 characters. Resource URLs must use HTTPS on one of these exact hosts: `bandit.readthedocs.io`, `cheatsheetseries.owasp.org`, `cwe.mitre.org`, `developer.mozilla.org`, `docs.astral.sh`, `docs.github.com`, `docs.python.org`, `fastapi.tiangolo.com`, `owasp.org`, or `peps.python.org`. The backend validates these links but does not fetch them.

This contract does not change `ReviewFinding` or observation provenance. Older canonical issues without `explanation` and legacy reviews without canonical issues remain valid. Existing AI candidate generation continues to return findings; canonical issue explanations are generated by the separate post-reconciliation path described below.

### Canonical issue explanation generation

For live reviews with learning enabled, the backend requests explanations after observation reconciliation and before persistence. Each canonical issue is one explanation unit; linked observations supply source-attributed messages, rule/tool provenance, evidence, and uncertainty cues. Existing downloaded source files or matching diff hunks may contribute a small excerpt near the issue's reported line. Full source files are not sent by this explainer. Demo reviews retain their curated content and do not make an explanation request.

Requests are batched by at most three issues and at most 32,000 characters including the serialized JSON and prompt framing. Each issue includes at most six observations, two evidence strings per observation (300 characters each), and up to 1,600 characters of nearby code context. Context is selected and bounded before JSON serialization; serialized prompts are never truncated. Responses are capped at 96,000 characters and validated per issue against the `IssueExplanation` schema. These initial limits bound latency and provider usage while retaining source diversity; they can be tuned based on observed context quality and provider limits.

The `tool_results` entry named `issue_explanations` reports `completed`, `partial`, `unavailable`, `not_needed`, or `not_requested`, with batch and issue counts. Invalid or missing explanations are omitted; valid results from other issues/batches are retained. Provider or validation failures do not fail the review or discard findings, observations, or canonical issues. AI explanations are advisory: the service cannot guarantee a root-cause interpretation or correction is accurate, does not apply fixes, and does not verify code examples or run tests. Resource links are schema-allowlisted but are not fetched or checked for availability.

### Suggested fix contract (Phase 3 Stage 1)

`CanonicalIssue.suggested_fixes` is an additive list, defaulting to empty for existing and legacy records. Each `SuggestedFix` is one contiguous replacement in one Python file, with a repository-relative path, one-based inclusive line range, exact expected original code, and proposed replacement code. The expected code must contain exactly the number of lines identified by the range. Code fields are limited to 20,000 characters each; the change summary to 500 characters; rationale to 2,000; and up to five limitations of 500 characters each are allowed. Up to five proposals may be attached to an issue.

Every proposal retains a full base commit SHA (40- or 64-character hexadecimal) and may include a full file blob SHA. Generation state is `generated`, `stale`, or `conflicted`: only an actual generated proposal is represented as a `SuggestedFix`; unavailable or failed generation outcomes must be reported separately and must not be fabricated as empty proposals. Decision state is independent and is `pending`, `accepted`, or `rejected`. An optional `decided_at` timestamp records when a decision was made. An accepted decision means only that a developer recorded acceptance inside PR Mentor; it does not apply code, write to GitHub, create a commit, or change a branch. Stage 1 defined the contract only; it added no generation, decision endpoint, persistence behavior, patching, or validation.

### Fix validation contract (Phase 4 Stage 1)

Each `SuggestedFix` additively carries `validation_reports`, defaulting to an empty list for legacy records and bounded to 20 attempts. A report is an immutable attempt with its own ID, fix ID, attempt number, trigger, engine version, timezone-aware timestamps, source snapshot identifiers when required by the provenance profile, bounded check results, evidence references, limitations, and a report-level status. Checks retain required/optional status, provenance profile, tool and version, configuration digest, timing, finding-count deltas, evidence references, and limitations. Evidence is referenced by ID and metadata; raw source files and logs are not embedded in the contract. Reports require unique IDs and attempt numbers per fix; check IDs are unique within each report.

Report status semantics are deterministic and validated against the authoritative aggregator: `failed` means any check failed, including an optional check, or a report-level failure is fatal; `passed` requires at least one required check and every required check to pass; `partial` means required evidence includes a pass or partial result but remains incomplete, or an unavailable report-level failure interrupted otherwise passing checks; `inconclusive` means a required check or report-level failure could not reach a conclusion; `unavailable` means required checks could not run and none passed or were inconclusive, or a report-level failure prevented checks from running; `not_run` means there are no required checks or all required checks were skipped/not run. Check failures and report-level `failed` outcomes take precedence. A report-level failure has its own bounded `code`, `status`, and `reason`; it is not represented as an artificial check. At check level, `skipped` is distinct from `not_run` and never counts as passing.

New reports use schema version `2`. Passing checks must include timezone-aware start/completion times and evidence references. The provenance profile defines additional requirements: `source_analysis` requires a report snapshot, tool name/version, configuration digest, and `tool_result` or `finding` evidence; `snapshot_integrity` requires a report snapshot and a `source_snapshot` evidence reference but does not require tool metadata; `ai_assessment` requires a report snapshot, tool/model name and version, and a `tool_result` reference, while configuration digest is optional; `non_source` requires evidence and timestamps but does not require a source snapshot or tool metadata. For every passing source-based profile, the report snapshot must identify the exact evaluated commit (`checked_head_sha`), original file (`baseline_blob_sha`), and reconstructed proposed file (`proposed_blob_sha`), each as a full 40- or 64-character hash. The baseline and proposed blob hashes identify different versions and must not be substituted for one another. Passing reports require a completion timestamp. Snapshot-based reports must point to the suggested fix's file.

Schema version `1` remains readable for existing history. `provenance_profile` preserves the profile originally declared by v1 (or remains null if none was declared); `effective_provenance_profile` records the guarantee supported by the available history. A v1 source-based check without the required commit and blob identifiers is classified `legacy_unverified` while retaining its original profile, report status, snapshot fields, and schema version. Missing hashes and evidence are never fabricated. The historical `status` is archival and does not assert current verification. V1 reports with complete provenance remain readable and retain their effective profile. New v2 reports require a current declared profile and matching effective profile; `legacy_unverified` is rejected. This compatibility layer is schema-level and requires no adapter migration. The pure aggregator is in `app/services/fix_validation.py` and performs no I/O.

Validation state is independent from fix generation state, developer decision state, and canonical issue status. A passed report is evidence about only its recorded snapshot and checks; it does not imply a developer accepted the proposal or that the issue is resolved. Stage 1 defines the schema and deterministic aggregation contract. Source validation and Stage 6 test execution each append immutable attempts to the owning fix history. Execution checks use the distinct `test_execution` provenance profile and reference the owner-scoped execution result. A passing execution without a same-snapshot required `source_analysis` or `snapshot_integrity` check is reported as inconclusive. Execution does not turn test generation into a test result or semantic review into deterministic evidence.

### Static and structural fix validation (Phase 4 Stage 3)

`app.verification.source_analysis.validate_static_fix()` accepts only an eligible `FixEligibilityResult` from Stage 2. Before any analyzer runs, it independently reconstructs the proposal and verifies the complete baseline and proposed Git blob hashes against the Stage 2 snapshot. Ineligible fixes or inconsistent source/snapshot pairs produce a report-level failure; they do not produce synthetic failed checks.

Ruff and Bandit analyze the baseline and proposed source as separate files in unique temporary directories. Each analyzer uses its installed Python module, a fixed explicit configuration, a restricted environment without GitHub or LLM credentials, no shell, bounded timeout, one-megabyte stdout/stderr caps, a 2,000-finding cap, and a two-process global concurrency bound. Ruff runs isolated from repository configuration and without its cache. Bandit uses an explicit empty config and includes low-severity, low-confidence findings. Tool version and canonical configuration digest must match across both source versions or that analyzer check is inconclusive. Ruff/Bandit and syntax checks are independent required checks; a failure in one analyzer does not erase another analyzer's evidence. Each report check references digest-identified output and finding-comparison evidence, while the returned `StaticValidationOutcome.evidence_payloads` holds the corresponding bounded bytes for a later persistence integration.

Finding reconciliation is deterministic and multiset-based. Exact normalized tool, file, rule, message, context, severity, and confidence identity is matched first; line numbers do not define identity, so moved diagnostics remain unchanged and are marked relocated. A unique remaining same-tool/file/rule pair with changed diagnostic representation is `modified`. Where multiple such candidates remain, or only weak rule evidence exists, the result is `uncertain`; it is not guessed as introduced or resolved. Clearly unmatched diagnostics are introduced or resolved. Bandit severity and confidence remain separate fields. Changed-line attribution reuses `added_lines_by_file()` over a computed baseline/proposed unified diff and is marked uncertain when the diff cannot be mapped reliably.

Python structural validation uses `ast.parse()` on both source strings. It records syntax errors as evidence and compares them with the same finding reconciliation rules. It does not import modules or execute code. A successful parse does not establish type correctness, runtime behavior, business correctness, or security. The authenticated validation endpoint appends bounded reports to the suggested-fix history; raw analyzer evidence payload storage is still not integrated. Analyzer subprocesses are bounded but are not an OS sandbox, and on Windows process-tree termination remains limited. Untrusted generated tests use the separate Stage 6 sandbox path.

### Type checking and additional quality analysis (Phase 4 Stage 4)

Stage 4 adds one selected type checker, mypy, through `app.verification.mypy_runner.run_mypy_source()` and `app.verification.additional_analysis.validate_static_fix_with_quality()`. The latter runs the approved Stage 3 validation first, then appends an independent required `mypy-comparison` check to that same Stage 1 schema-v2 report. A mypy failure does not erase Ruff, Bandit, or AST results. Mypy runs separately on the exact Stage 2 verified baseline and proposed file strings in isolated temporary directories. The runner uses a fixed Python 3.12 configuration, disables incremental cache and site-package discovery, ignores repository mypy configuration, does not load project plugins, and does not import or execute the repository source. Source-provided `# mypy:` configuration and `# type: ignore` suppressions cause an inconclusive result rather than allowing changed code to suppress diagnostics. Its configuration digest, tool version, timestamps, bounded output evidence, normalized diagnostics, and baseline/proposed deltas are recorded in the existing validation outcome.

The available context is one Python file. Standard-library typing information is available; project modules and third-party type stubs are not supplied or installed. Missing imports and missing stubs therefore make the mypy check `inconclusive`, never `passed`; [mypy documents unresolved imports and missing stubs](https://mypy.readthedocs.io/en/stable/running_mypy.html#missing-imports) as reduced analysis context. The fixed policy checks untyped function bodies but does not require every function to declare annotations; untyped parameters remain `Any`, so those flows receive weaker checking. Strict mode is not enabled because the repository has no agreed type policy and the single-file service should not impose a new annotation-style rule. The analysis is not a project-wide or runtime correctness proof. The analysis framework is intentionally a small registry of typed source-runner registrations sharing Stage 3's `SourceToolRun`, `compare_findings()`, bounded process runner, temporary source writer, evidence references, and Stage 1 report/check schemas. Currently only Python is supported; C, C++, and Java are not implemented.

#### Stage 4 candidate evaluation

This is a qualitative evaluation, not a claim of universal tool accuracy or a fabricated score. We did not run a same-project head-to-head benchmark for unavailable candidate tools. The environment inventory found Node.js 24.22.0, but no Pyright, mypy, Semgrep, or pip-audit installation. A package-index dry run found mypy 2.4.1 and Semgrep 1.184.0 available; Semgrep's current distribution resolved a substantially larger dependency set, including MCP, OpenTelemetry, and Windows-specific packages. Repository evidence shows the backend has `requirements.txt` only: no `pyproject.toml`, supported lockfile, or baseline/proposed dependency-manifest input. Stage 2 currently supplies one verified Python source pair.

Local timing measurement: on Windows with Python 3.12 and mypy 2.4.1, five runs over the same clean, annotated two-argument function fixture had a median `run_mypy_source()` wall time of 1.12 seconds and median subprocess time of 0.80 seconds. This small one-file fixture measures local startup and execution only; it is not representative of a repository-wide scan and does not compare mypy against Pyright or Semgrep.

Semgrep [local rules are YAML](https://semgrep.dev/docs/writing-rules/glossary), and Semgrep's open-source engine supports per-file taint analysis; its documentation says inter-file analysis is limited to proprietary functionality. This makes carefully selected local rules a future candidate, not a present claim. No registry rules, PR-supplied configuration, or rule plugins are downloaded or executed in Stage 4. [pip-audit's security model](https://github.com/pypa/pip-audit#security-model) warns that auditing arbitrary requirement inputs can involve dependency resolution comparable to installation. Dependency vulnerability analysis, package installation, setup scripts, and resolver execution are not performed.

The mypy runner uses Stage 3's argument-array subprocess helper, controlled environment, source-size limit, two-process concurrency bound, maximum 20-second timeout per subprocess, and one-megabyte output caps. Baseline and proposed runs must have equal tool versions and configuration digests. Finding comparison reuses Stage 3's deterministic comparison categories and preserves uncertain matching. These controls bound routine subprocess behavior but do not form a full OS sandbox. In particular, Stage 3's Windows process termination does not provide a general process-tree/job-object guarantee; this is another reason Semgrep, which may launch native worker processes, remains deferred.

Stage 4 generates no AI opinions, does not run tests, and does not implement dependency reachability, API orchestration, persistence changes, or a frontend workflow. A mypy pass is only evidence that the submitted single-file snapshot produced no new diagnostics under the recorded configuration and available import context.

### Isolated fix generation (Phase 3 Stage 2)

`app.ai_review.fix_generation.generate_suggested_fixes()` is a bounded service called by orchestration only when `include_suggested_fixes` is true for a live review. It accepts canonical issues, repository owner/name, the PR head SHA, and parsed PR diff context. It fetches each relevant Python file at that exact head revision through the existing bounded `get_file_content()` service, selects at most 20 numbered lines around the issue, and includes a small matching diff-hunk excerpt plus bounded observations and any existing explanation. It does not send whole files to the model. The file blob SHA is derived locally using Git's blob hash over the exact UTF-8 source bytes; the model cannot supply or override snapshot metadata. `base_commit_sha` records the PR head revision used as the proposal's source snapshot.

The service processes at most five issues and makes at most five LLM calls per invocation, one call for each issue with sufficient source context. Source fetches time out after at most 20 seconds each, provider calls after at most 60 seconds each, and the total service budget is 120 seconds. Existing source files remain subject to the 100 KB retrieval limit. Each prompt is at most 24,000 characters and each response at most 32,000 characters. Unsupported paths, missing/ambiguous line ranges, removed/unavailable files, or oversized context produce a separate `insufficient_context` outcome without an LLM call. An unconfigured provider is `unavailable`; attempted but malformed, timed-out, or unverifiable generation is `failed`; a model refusal is `no_proposal`; excess issues are `skipped_limit`.

The service treats model output as untrusted. It verifies the returned issue ID and exact file path, requires the replacement range to stay within the issue lines and bounded source excerpt, compares `expected_original_code` exactly against the retrieved numbered source lines after line-ending normalization, rejects no-op replacements, and then validates the server-constructed `SuggestedFix` against the schema. The file blob SHA covers the exact UTF-8 source bytes. Fix IDs, language, decision status, generation status, timestamp, commit SHA, and file blob SHA are supplied or derived by the backend. Results are returned separately and do not mutate input issues, local files, or GitHub. Generation status describes actual proposals; unavailable and failed outcomes are not empty fix records. This stage does not apply, persist, accept, reject, or validate proposals.

### Suggested fix orchestration (Phase 3 Stage 3A)

Live review requests may opt in with `include_suggested_fixes: true`; the default is `false`, so existing requests make no additional fix-generation calls. Demo reviews never invoke fix generation. For opted-in live reviews, orchestration passes the reconciled canonical issues and the PR head SHA captured during ingestion to the Stage 2 service after the existing explanation step. The service remains sequential and retains its five-issue/five-call limits. Successful proposals are attached to their canonical issues; per-issue outcomes are reported in a `fix_generation` entry in `tool_results`. `skipped_limit` is rendered as `skipped`; `generated`, `unavailable`, `insufficient_context`, `failed`, and `no_proposal` remain distinct. Outcomes are not `SuggestedFix` records and do not change decision status.

Fix generation is best effort: failures do not discard findings, observations, canonical issues, or explanations, and do not downgrade the overall review status. The completed response is persisted once through the existing whole-review store operation; SQLite and MongoDB retain proposals and outcome reporting in their existing JSON/document payloads. Stage 3A did not detect conflicts, re-fetch the PR head, apply code, or validate generated changes.

### Deterministic fix relationship analysis (Phase 3 Stage 4, conflict detection)

For opted-in live reviews, `app.services.fix_analysis.analyze_fix_relationships()` runs after Stage 3A generation and reports pairwise relationships in the review's `fix_analysis` tool result. It compares same-file proposals only when they have compatible source snapshots: the same base commit with no contradictory blob hashes, or matching file blob hashes. Identical path/range/original/replacement proposals are reported as `duplicate` and both remain attached. Overlapping inclusive ranges with different replacement code on a compatible snapshot are `definite_conflict`; affected proposals are marked `generation_status="conflicted"` without changing `decision_status`. Different-file pairs and other comparable pairs with no direct conflict are `no_detected_conflict`. Same-file pairs with incompatible snapshot metadata are reported as `incompatible_snapshot` and make analysis partial; no conflict status is inferred.

Analysis is capped at 25 proposals. No-detected-conflict does not mean proposals are independent or safe to combine. This stage does not check freshness, call GitHub, detect import/symbol dependencies, alter proposals other than the definite-conflict status, or apply code. Demo reviews retain their existing behavior; legacy records without analysis metadata remain readable.

### Suggested-fix freshness verification (Phase 3 Stage 4)

For opted-in live reviews, `app.services.fix_freshness.verify_fix_freshness()` runs after fix generation and conflict analysis. It fetches the current PR head through the existing GitHub client with its process-local 60-second response cache and in-flight coalescing bypassed. It then fetches each distinct proposal file once at that immutable head SHA and compares Git blob hashes with the proposal's recorded `file_blob_sha`. A changed PR head does not by itself make a proposal stale: an unchanged target file remains `current`; any changed target file is conservatively `stale`, regardless of whether the proposed lines appear unchanged. Missing or invalid snapshot metadata, inaccessible/oversized files, unconfirmed deleted or renamed paths, API failures, and rate limits are `unverifiable`.

Freshness outcomes are stored in the `fix_analysis` tool result under `freshness`, separately from conflict `relationships`. Verification never rewrites proposal source metadata or code, changes `decision_status`, removes proposals, or invalidates the review. It is bounded to 25 proposals and a 90-second review budget, with a 15-second maximum per GitHub operation. Demo and legacy reviews are not re-verified; old stored records remain readable without freshness metadata. Verification is read-only and does not apply fixes or write to GitHub.

### AI-powered test generation (Phase 4 Block 2 Stage 5)

`app.ai_review.generated_tests.generate_tests_for_fix()` creates candidate pytest code for one existing `SuggestedFix`. It first rechecks fix eligibility at a freshly retrieved immutable PR head using the Stage 2 service. The context builder independently verifies baseline and reconstructed proposed Git blob hashes against that snapshot, checks the fix-to-issue association, and supplies bounded AST-focused source excerpts with repository paths and line references. It includes issue metadata and labels any existing AI explanation as unverified context. It does not retrieve related tests or files from a moving branch; unavailable context is reported explicitly.

The typed `app.schemas.generated_test` contract binds each candidate to its fix, canonical issue, repository, snapshot ID, base commit, checked head, and baseline/proposed blob hashes. The deterministic quality screen parses candidate strings with Python's AST only. It rejects malformed code, non-pytest function shapes, missing assertions, ungrounded references, dynamic execution, direct file operations, and prohibited system/network imports. Other quality dimensions remain categorical review guidance; they are not correctness scores.

Generation statuses (`generated`, `partial`, `rejected_by_quality`, `failed`, `unavailable`, and `not_attempted`) describe generation and static screening only. Every candidate has `execution_status="not_run"`; the Stage 1 check adapter is optional and `not_run`, and candidate references use evidence kind `other`. The authenticated generation endpoint returns candidates. Execution submission persists the selected candidate with its job payload, without changing the fix or issue decision. Generation itself never executes tests or claims verification.

Each request handles one fix and makes at most one provider call, with a 60-second total limit, a 35-second provider timeout, a 24,000-character context limit, a 30,000-character prompt limit, a 64 KiB streamed response cap, at most six accepted tests, and bounded rejection/ambiguity metadata. Token usage is `null` because this provider client does not expose reliable usage metadata. Generated candidates are not independently saved as a history record; once submitted for execution, the candidate is retained with the durable execution job. There is no runtime dependency installation, repository write, or host import/execution of candidate code. A request fingerprint is returned for caller-side deduplication.

Generated tests are untrusted suggestions, not evidence that a fix works. They can contain logically incorrect assumptions despite static screening and require human review. Stage 6 consumes an explicitly selected candidate only after a separate authenticated submission, runs it in the dedicated disposable worker, and never promotes generation status to passed without actual test results.

### Secure isolated test execution (Phase 4 Block 2 Stage 6)


`app.test_execution.execution_worker` is a dedicated durable coordinator, deployed with `deploy/pr-mentor-test-execution-worker.service`. Authenticated API routes accept a generated candidate, recheck current source eligibility, and persist an owner-scoped idempotent job in the configured SQLite or MongoDB store. The trusted coordinator process can access the configured persistence store to claim jobs; its child gets a strict environment allowlist, with database, GitHub, AI, and cloud credentials excluded. Nothing from the coordinator environment is copied into the Docker container. Job results and the candidate are persisted; queued jobs can be cancelled, running jobs receive a cooperative cancellation request, and expired worker leases fail closed rather than rerunning an attempt. The child calls `app.test_execution.worker.execute_generated_test()`, which independently checks repository/review/issue/fix/test identity, recomputes Stage 5's canonical snapshot ID, verifies both Git blob hashes, reconstructs proposed source from the verified baseline and fix, and rejects stale, mismatched, or unsafe path inputs. It runs the same generated test in two newly created, separately cleaned containers, each receiving only the exact baseline or proposed source file plus the same test; no checkout, branch, arbitrary path, frontend source, or user-supplied command is accepted.

The worker runtime is replaceable through `ExecutionRuntime`. `DockerGVisorRuntime` fails closed unless Docker is rootless, cgroups v2 is active, `runsc` is registered, and the configured sandbox image exists locally with the expected Python/pytest labels. `PR_MENTOR_TEST_EXECUTION_IMAGE` must be an immutable `name@sha256:<64 lowercase hex>` digest; the development default is unset, so execution is unavailable until explicitly configured. Build `sandbox/Dockerfile` with a trusted Python 3.12.10 base image pinned by digest, then publish/resolve the resulting sandbox image and configure its final immutable digest. The sandbox image contains only Python 3.12.10 and the locked pytest 8.4.2 toolchain. Runtime package installation and network access are disabled.

The sandbox runs with `--runtime=runsc`, rootless Docker, `--network=none`, a read-only root filesystem, UID/GID 65532, dropped Linux capabilities, `no-new-privileges`, no inherited worker environment, one read-only input bind mount, and bounded no-exec `/tmp` and `/dev/shm` tmpfs storage. It receives no Docker socket, credentials, repository checkout, or writable host mount. Pytest is launched only by the trusted in-image `sandbox/runner.py`; plugin autoload, conftest discovery, and project pytest configuration are disabled. The runner starts only `python -I -m pytest` with fixed arguments and bounds combined test output before returning separate stdout/stderr fields.

Defaults are 30 seconds wall time, 1 CPU, 512 MiB memory, 32 processes, 64 MiB scratch, 128,000 bytes combined output, and 2 concurrent executions. Validated environment overrides use `PR_MENTOR_TEST_EXECUTION_TIMEOUT_SECONDS`, `CPU_COUNT`, `MEMORY_BYTES`, `PROCESS_COUNT`, `SCRATCH_BYTES`, `OUTPUT_BYTES`, and `CONCURRENCY` with the `PR_MENTOR_TEST_EXECUTION_` prefix. Docker/cgroups enforce CPU, memory, and process limits; gVisor adds syscall isolation; Docker and the worker enforce wall time; the tmpfs bounds scratch; the in-image launcher and worker bound output; and the worker semaphore bounds concurrency. Limits outside the conservative ranges are rejected.

Execution statuses remain separate from test generation. Only pytest exit code zero can produce `passed`; pytest assertion failure exit code 1 is `failed`; timeout, cancellation, missing runtime prerequisites, rejected inputs, and infrastructure errors remain distinct. Launcher/usage errors, output-limit events, resource-limit events, and unconfirmed cleanup are infrastructure errors, never test failures. Cleanup is attempted on every created container and temporary artifact; unconfirmed cleanup overrides any normal test outcome and prevents starting the second attempt. Bounded execution results retain separate baseline and proposed outcomes, source and identity provenance, runtime/image/tool versions, timing, exit code, output and resource metadata, and persist with the owner-scoped job. A regression is detected only when the same test fails on the baseline and passes on the proposed source with matching runtime and resource configuration; passing on both is `not_reproduced`, and incomplete or mismatched evidence is unavailable or inconclusive. A completed job is also attached idempotently to the exact owning fix's validation history, only when review, issue, fix, repository, and snapshot identities still match. The status endpoint returns that report so the frontend can display the persisted attempt after polling or refresh. Even a detected regression is limited to the generated test's behavior and is not a general correctness verdict for the fix.

This development environment is Windows and has no Docker CLI, rootless Linux daemon, gVisor runtime, or cgroups v2 worker. Unit tests can validate contracts and fail-closed behavior, but Linux integration tests and real sandbox isolation cannot be verified here. Deploy only on a dedicated Linux host/service with rootless Docker, gVisor, cgroups v2 controllers, an approved immutable sandbox image digest, and no application secrets. Rootless Docker and gVisor provide defense in depth, not an absolute guarantee against every escape or denial-of-service scenario. Windows process-tree behavior and actual Linux cleanup guarantees require deployment validation.

Residual cleanup limitation: the child process's `finally` block removes temporary artifacts and the named container on normal returns, failures, timeout, and cooperative cancellation. A hard child/worker/host crash cannot execute that block. The in-image runner bounds its own pytest lifetime, so untrusted code stops at its deadline, but the stopped-container record and staged host files can remain until cleanup. An age-based reaper has a systemd service/timer under `deploy/` and removes only stale PR Mentor-labeled containers and stale `prmentor-stage6-*` temporary directories. This path is unit-tested but not exercised against Docker on Linux. Real rootless Docker/gVisor/cgroups v2 integration remains a production gate. Deterministic reports now combine same-snapshot source checks with each execution attempt; independent AI semantic assessments are still separate opinions, and evidence references do not replace an independently retained artifact store.

## Module boundaries and team ownership

The public request/response schemas in `app/schemas/` and route paths above are shared contracts. Keep them stable while replacing internals.

- **Member 1 — GitHub ingestion:** `app/github_service/parser.py`, `client.py`, `pull_requests.py`, and `files.py`. `parse_pull_request_url()` validates a GitHub PR URL; `fetch_pull_request()` returns a `PullRequestBundle` with typed metadata, statuses, and patches. Requests go only to the fixed GitHub API host, use timeouts, paginate with a cap, and report upstream failures explicitly.
- **Member 2 — static analysis and verification:** `app/verification/`. `path_validation.py` is a security boundary: retain its checkout containment and symlink checks. Ruff and Bandit consume only Python files materialized into a temporary directory. `test_runner.py` reports unavailable; PR code is never executed on the host.
- **Member 3 — AI review:** `app/ai_review/client.py`, `prompts.py`, and `reviewer.py`. Replace the OpenAI-compatible transport behind `complete_json()` while keeping `generate_candidates()` schema-validating and provider-independent. Credentials are environment-only. Missing credentials and provider errors produce unavailable tool status, never fabricated AI findings.
- **Integration owner:** `app/services/review_orchestrator.py` coordinates modules and partial failures. `app/routes/`, `app/schemas/`, `app/database/`, and `app/main.py` own the API, persistence boundary, and application configuration. Coordinate contract changes here rather than having module owners independently change routes or frontend types.

## Runtime behavior and security

Demo mode returns stable educational findings labelled with source `demo`; it does not fetch or analyze the submitted repository. Live mode fetches GitHub metadata and diffs, retrieves at most 20 bounded Python files, runs available static analyzers in a temporary workspace, and includes AI findings only when configured. Tests are not run; the response explicitly says so. Tool unavailability creates `partial` status and warnings. The submitted repository URL is parsed and restricted to HTTPS `github.com`; server requests use a fixed `api.github.com` base to avoid arbitrary outbound destinations.

SQLite and MongoDB implement the replaceable `ReviewStore` interface. Reviews, saved PR links, and learning attempts survive process restarts. A failed database write returns an API error; the service does not claim success.

### Account, ownership and analytics foundation

The API supports local email/password registration and login, opaque server-side sessions, logout, and `/api/auth/me`. Passwords use the Python standard-library scrypt KDF. Session cookies are HttpOnly, SameSite=Strict, and Secure by default; set `PR_MENTOR_COOKIE_SECURE=false` only for local HTTP development. Production deployments must serve HTTPS, retain the Secure default, configure exact `PR_MENTOR_CORS_ORIGINS`, and use managed secret/storage controls. Authentication attempts are rate-limited by hashed account and remote-address buckets. This is a local account foundation, not GitHub OAuth: email addresses are not verified, password reset and recovery are not available, and production account abuse protections still need operational review.

Review, saved-link, and learning records are scoped to the server-authenticated user. SQLite adds nullable ownership columns without deleting old records; MongoDB stores an owner field. Historical records whose owner cannot be determined remain preserved but are not assigned to the first new account. Review endpoints deny cross-account reads and writes. Live PR analysis first checks repository visibility and refuses private repositories because a shared `GITHUB_TOKEN` is not an end-user authorization credential. User-connected GitHub OAuth is deferred.

Workspaces use explicit membership roles, email-bound expiring invitations, and explicit per-review share links. Workspace identifiers do not grant access; backend routes re-check membership and write permission. Shared review updates preserve the account that originally owns the review. Workspace records and benchmark datasets/runs are persisted in SQLite and MongoDB.

The active frontend sends cookie credentials, includes account registration/sign-in, and shows personal and workspace review insights from stored records. Personal analytics uses an exact review count and analyzes at most the latest 100 owned reviews; workspace insights analyze at most the latest 100 explicitly shared reviews. Provider latency, cost, and labelled accuracy are returned as unavailable until genuine measurements/labels are recorded. Suggested-fix accept/reject records user intent only, and acceptance requires a current-snapshot result recorded in the live review. No GitHub write is performed.

### Human-labelled benchmark workflow

`/api/benchmarks` stores account-owned datasets with explicit `labels_complete` flags, human finding signatures (`category|severity|file_path`), optional human review-outcome labels, and optional accepted/rejected fix labels. A run evaluates the linked saved live review output; demo/sample reviews and missing predictions are excluded and make the run incomplete. Each run stores label/prediction signatures, review IDs, dataset timestamp, actual provider/model and request settings, fallback attribution, code-review prompt version and hashes, and measured durations. Runs replay immutable result snapshots and do not rerun a model. Fresh inference evaluation remains deferred: it requires a reproducible source snapshot plus a bounded, durable model-evaluation job; replay records alone are not treated as a fresh run. Precision/recall use exact human-labelled finding signatures; outcome accuracy is calculated only for cases with an explicit outcome label. Provider-reported token usage and measured request latency are included only when returned/recorded; cost remains null because no provider pricing telemetry is captured. No sample data is treated as ground truth.

`LLM_MODEL` remains the default model. Task-specific models continue to use the OpenAI-compatible endpoint and key. Provider routing accepts `LLM_PROVIDER`/`LLM_PROVIDER_<TASK>` and comma-separated `LLM_FALLBACK_PROVIDERS`/`LLM_FALLBACK_PROVIDERS_<TASK>`; named providers use `LLM_<NAME>_API_KEY`, `LLM_<NAME>_API_BASE_URL`, and optional model/concurrency settings. Retries and provider chain length are bounded, fallback attempts are observable, and both structured transport responses and task-specific schemas are checked before use; an untried configured provider is tried after a schema-invalid response. Usage tokens and request latency are recorded only when actual response metadata is available; no cost is inferred. All registered adapters currently use the OpenAI-compatible chat-completions protocol; native provider-specific protocols are not implemented. Durable review and isolated execution jobs are implemented. Review jobs retry only explicitly classified safe GitHub read failures with exponential backoff (maximum three attempts); expired worker leases fail closed because the work may already have incurred provider-side effects. Lease tokens fence stale workers from heartbeating, completing, or failing a job after losing ownership. Isolated generated-test jobs also fail closed on expired leases and never retry untrusted code automatically. Both workers heartbeat while active and clean local temporary resources in `finally` paths; OS hard-crash cleanup relies on the Stage 6 reaper. Bounded repository structure analysis now includes a capped repository manifest, changed-file-prioritized Python symbols/imports, internal import edges, and bounded dependency identifiers while reusing already fetched PR sources. AI semantic assessment remains probabilistic and is not deterministic verification. Generated-test execution is explicitly queued to the dedicated worker and is never run in FastAPI. Stage 6 still requires a dedicated Linux deployment and real rootless Docker/gVisor/cgroups v2 verification; this Windows environment cannot establish those isolation guarantees.

The orchestration layer has no dependency on the nested backend repository from Ritik's fork. `backend/` is an ordinary tracked directory in this canonical repository.
